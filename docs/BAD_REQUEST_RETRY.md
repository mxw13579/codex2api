# 通用 Bad Request 的独立重试

> 默认关闭。本地实现与测试不代表已经部署或启用。该策略用于缓解偶发错误，不代表已查明 HTTP 400 的根因；重试成功也不能证明是代理或账号问题。

## 设置

管理后台「重试」区域新增 **Bad Request 独立重试**。三个字段通过现有 `GET/PUT /api/admin/settings` 读写：

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `bad_request_retry_enabled` | `false` | 独立开关；关闭保留原行为 |
| `bad_request_retry_max_retries` | `1` | 0–10 的整数，表示额外重试次数；0 不重试 |
| `bad_request_retry_switch_account` | `false` | false：同号重试；true：范围内换号重试 |

例如一次最多额外重试两次，允许换号：

```json
{
  "bad_request_retry_enabled": true,
  "bad_request_retry_max_retries": 2,
  "bad_request_retry_switch_account": true
}
```

PUT 省略或传 `null` 的字段不变；错误类型、非整数、越界返回 400。关闭开关不清空已保存的次数和换号偏好。策略单独存入 `system_settings.bad_request_retry_policy` JSON 文本列；PostgreSQL/SQLite 增加兼容列，普通设置保存不覆盖此列。部分更新在事务中合并，提交成功后才更新内存。

HTTP 入口在读取请求体前固定快照，WS 入站每轮单独固定快照；热更新只影响后续请求/轮次。内部直接调用已准备好的图片执行器时，在执行器入口固定快照。

## 精确匹配与预算

只处理真正的**上游 HTTP 400**，且完整 JSON 对象只有：

```json
{"detail":"Bad Request"}
```

允许 JSON 格式空白和等价字符转义，但不接受重复字段、额外字段、大小写不同或带前后空格的消息。匹配输入最多 1 KiB。以下均不属于本策略：

- 明确的参数、模型、上下文、加密内容、安全拒绝或图片 complexity 错误；
- `{"error":{"message":"Bad Request"}}` 等其他结构；
- HTML/纯文本/截断/读取失败的响应；
- HTTP 200 内的 SSE/WS 终态错误，或本地参数校验失败。

独立预算不消耗普通 `max_retries` 或 429 额度。若一直返回此错误，额外次数为 N 时最多发送 1+N 次；候选不足、取消或安全限制可更早停止。图片端点的独立尝试也不消耗原有普通尝试次数上限。其他种类错误继续按原策略处理，所以混合错误的总尝试数不一定是 1+N。

启用后，这个精确错误由独立策略负责；即使次数为 0 或已耗尽，也不会再交给 continuous catch-all 无限重试。关闭后保留原有策略，包括管理员之前显式设置的持续重试规则。沿用现有重试间隔、退避、取消与请求期限，不额外增加后台重放任务。

## 同号、换号与安全边界

- **同号**：释放失败尝试的租约，再重新申请原账号；重查账号可用性、并发、Key 范围、分组、模型、scope 额度及 ProMax 资格。同号不能获取时返回原 400，不悄悄改借其他号。容量溢出借号的原亲和保护继续保留，不因同号重试永久迁移会话绑定。
- **换号**：本请求内排除已经被该策略判定需换出的账号；只做一次正常候选选择，不清空排除表循环等待。没有合格候选时返回原 400，不越 Key/分组借号、不回退到已失败账号。代理随所选账号和既有路由规则确定，换账号不保证换出口 IP。
- 外部固定账号请求不启用此新策略。绑定中的续链不为换号解锁；只有已恢复完整、同所有者历史时，才允许用完整输入替代账号相关的 `previous_response_id`。不以丢弃历史或降低档位换取成功。
- 明确 `ultrafast` 仍只能使用认可的 ProMax，普通 fast/priority/default 保持原资格规则。
- 已输出正文/提交响应后不新增此类 HTTP 重试；safe-preflight 的窗口、次数和绑定保护继续生效，可能早于配置次数结束。
- 此错误发生在 HTTP 路径，后续专用尝试保持 HTTP，避免重新绕回 WS 握手；不会把明确要求上游 WS 的中转账号悄悄降为 HTTP，这类账号不作为专用重试候选。

覆盖 Responses、Chat Completions、Messages、Responses compact、图片生成/编辑，以及 WS 入站使用 HTTP 上游的错误路径。WS 传输自身的错误与流内错误保留原规则。

## 观测与验证

保留每次失败的原有正文日志、用量记录及尝试序号；重试标记沿用现有语义（该失败后是否计划重试）。控制台附加 `[bad-request-retry]`，只含账号内部 ID、专用次数和换号模式，不新增完整用户请求采集。若下一次选号失败或取消，计划重试不代表已经再次发出。

诊断关联与 HTTP/2 摘要修复见 [UPSTREAM_ERROR_DIAGNOSTICS.md](UPSTREAM_ERROR_DIAGNOSTICS.md)，与本重试策略是不同功能。日志有既有限长、异步丢弃等边界，不是完整审计账本。

测试包括严格匹配、预算隔离、普通/429混合错误、同号/换号、无候选、ProMax/Key/group/scope、scope 并发为 1、借号亲和保护、pin/完整续链、取消/读体失败、慢上传期间热更新、HTTP/WS轮次隔离，以及 PostgreSQL SQL 分支/SQLite 迁移和持久化、API 和前端字段保存。上游 fixture 都是合成数据和本机 loopback，不证明真实上游兼容性或生产容量；实际 PostgreSQL 集成、race 与浏览器行为须另行验证。

本次本地验证：最终 `go test -p 1 ./... -count=1 -timeout 10m` 全部通过（离线依赖、`GOMAXPROCS=2 GOGC=50`）；TypeScript 检查和前端生产构建通过；LF 源码副本的前端测试 426/426 通过。Windows CRLF 工作区仍触发三个已有换行敏感断言，未改动这些断言。之前两轮全量运行曾出现三个非新增用例失败（持续重试清理时序、后台质量任务进度、图片 catch-all 调用次数）；这些用例各重复十次通过，最终全量也通过，但不能据此证明不存在时序不稳定。当前环境未完成 race 测试；未连接真实 PostgreSQL、上游或改动线上。
